# 版本与发布规范

从v1.2.0开始统一管理系统版本。每轮系统更新交付到GitHub时递增版本，日常开发过程中无需每次保存都升版。

| 更新类型 | 规则 | 示例 |
| --- | --- | --- |
| 修复、兼容优化、文档与测试补充 | PATCH加1 | 1.2.0 → 1.2.1 |
| 向后兼容的新功能 | MINOR加1，PATCH归零 | 1.2.1 → 1.3.0 |
| 不兼容接口、数据或部署变更 | MAJOR加1，其余归零 | 1.3.0 → 2.0.0 |

根目录 `VERSION` 是唯一版本来源。`scripts/version.py` 同步Web与移动端package、两个package-lock的根版本、后端pom及uni-app manifest。移动端versionCode按 `major × 1000000 + minor × 1000 + patch` 计算，minor和patch限制为0～999，保证版本递增。

## 更新版本

在根目录运行，需要Python 3.9+：

```powershell
python scripts/version.py bump patch
# 新功能改用 bump minor；不兼容更新改用 bump major
```

命令同步版本并添加带TODO的更新日志条目，不会自动提交或推送。填写 `CHANGELOG.md` 的实际变化、验证结果及已知限制，再运行：

```powershell
python scripts/version.py check
```

版本不一致、更新日志缺失或仍有TODO时检查失败。GitHub Actions会在主分支推送、PR和版本标签推送时执行检查，标签必须与VERSION一致。初始化或修复误改时可用 `python scripts/version.py sync`，不要改动第三方依赖版本。

## 验证与提交

发布前按变化运行逻辑回归、Web／移动端类型检查、三端构建及后端测试。照片相关改动另外运行 `node scripts/test-photo-uploads.cjs`；移动环境复现步骤见[测试脚本说明](../scripts/README.md#移动端环境回归)。

确认差异只包含本轮要发布的内容，版本和更新日志与源码一并提交。已发布标签不得删除重建或强制移动。主分支与标签应指向同一个发布提交，例如：

```powershell
$releaseVersion = (Get-Content VERSION -Raw).Trim()
python scripts/version.py check --tag "v$releaseVersion"
git commit -m "feat(release): publish v$releaseVersion"
git tag -a "v$releaseVersion" -m "Shuyang Home v$releaseVersion"
git push --atomic origin main "v$releaseVersion"
git ls-remote origin refs/heads/main "refs/tags/v$releaseVersion^{}"
```

上面的commit命令要求先明确暂存本轮文件；不要把真实数据库、运行时凭据、缓存或本地测试输出加入Git。上传源码和标签不代表已经部署服务器或发布微信小程序。

## 版本化交付包

完成本版本三端与后端生产构建后，在根目录运行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/package-release.ps1
python scripts/verify-release.py
```

默认生成 `release/shuyang-home-v<版本号>/` 与同名ZIP，携带VERSION、CHANGELOG和SHA256清单。脚本按当前版本选择后端JAR；已有交付包不会覆盖。预览与本地启动也从VERSION选择JAR，停止预览按启动时记录的JAR识别进程，避免升版后误认进程。

Linux服务通过 `shuyang-home.jar` 链接运行选定的版本JAR。部署时更新链接并保留上一版本文件；数据库和配置按[启动与部署](启动与部署.md)备份。涉及不兼容的数据变更时，必须先写明迁移与回退方式。
