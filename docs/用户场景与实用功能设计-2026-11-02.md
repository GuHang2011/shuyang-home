# 沭阳之家：用户场景与实用功能设计

日期：2026-11-02。状态：本设计的八类服务已在v1.7.0实现首版，具体范围和未覆盖细节以[交付说明](生活服务与高铁悬浮窗-v1.9.0.md)为准；下文保留最初设计供后续迭代对照。

依据当前 v1.5.1 的项目说明、已有路线图和前端功能入口整理。主要面向在苏州生活、工作、创业的沭阳老乡，同时兼顾返乡与异地使用。以下需求是根据平台定位推导的假设，尚未经过真实用户访谈，不将其表述为已证实的用户需求。

## 设计基础

现有系统已提供会员管理、活动签到、论坛、资源交换、聊天、联系方式交换、相册、特产订单、投票、众筹和一凡说高铁。新增能力应嵌入这些入口，减少手机上的导航层级。

沿用用户确认的边界：H5 与微信小程序优先；广告人工审核展示；众筹只记录物资、服务、资金意向；特产在线下单、人工确认、线下结算。新增功能不改变这些交易方式。

此前已提出统一通知、收藏、候补、发布管理等基础能力，本方案引用这些能力作为依赖，并进一步设计具体服务场景。大字模式和表单体验可以作为公共界面改进单独推进。

## 功能与优先级

P1 表示建议优先试点，P2 表示在基础流程和运营负责人具备后推进。工作量为相对比较，不是工期承诺。

| 功能 | 用户要解决的问题 | 复用模块 | 优先级／相对工作量 |
| --- | --- | --- | --- |
| 新来苏州服务包 | 刚到一个城市，不知道该先办什么、去哪查 | 公告、指南、会员资料 | P1／中 |
| 老乡帮办 | 发布求助后，不清楚谁接了、办到哪一步 | 互助、会员、聊天 | P1／中高 |
| 规范岗位卡 | 招聘帖子缺薪资、地点、时间，联系后才发现不合适 | 互助中的求职招聘 | P1／中 |
| 活动出行卡 | 报名成功后，集合地点、时间、联系人分散 | 活动、签到、天气 | P2／中 |
| 便民服务名片 | 想找维修、摄影等服务，却不知道谁愿意提供 | 会员名录、联系方式交换 | P2／中 |
| 特产到货预告与自提预约 | 想买的商品没货；取货时不知道去哪、何时可取 | 特产、订单、通知 | P2／中 |
| 共建项目执行公示 | 认领了物资或服务，却看不到后续进展 | 众筹、图片上传、通知 | P2／中 |
| 失物招领与认领核验 | 丢失物品后缺少统一入口，认领时难以确认归属 | 互助、图片、聊天 | P2／中 |

## 1. 新来苏州服务包

**场景：** 新会员入会后需要租房、求职、办理社保或了解子女入学流程。

- 入口：首页“生活服务”，入会成功页提供可跳过的“新来苏州”入口。
- 用户主动选择所在城市／区县与所需事项，例如找工作、租房、社保、入学；不要求先授权定位。
- 每个事项包含适用地区、办理条件、材料清单、官方入口、核验日期和内容维护人。
- 用户可保存清单、勾选已准备材料、记下个人进度；勾选仅表示本人准备情况。
- 找不到答案时，可带上指南标题发起帮办；不自动携带用户填写的个人材料。
- 指南支持“信息有误／链接失效”反馈，维护人核对后更新；过期内容显示待核验提示。

**流程：** 选择事项 → 阅读适用条件 → 保存材料清单 → 自行办理 → 标记完成或发起求助。

**验收：** 切换地区后不会继续显示其他地区的适用说明；清单进度跨端一致；过期指南可见更新时间和纠错入口；未提交表单不会要求上传身份证等材料。

**试点：** 先由明确的维护人整理 5～10 条有官方来源的高频指南，再开放更多分类。

## 2. 老乡帮办

**场景：** 需要修改简历、学习手机操作、获得办事指引或临时生活协助。允许单向提供帮助，无须拿资源交换。

- 入口：互助页新增“我需要帮助／我能帮忙”筛选，保留现有信息浏览方式。
- 求助字段：类型、问题描述、所在区县、期望完成时间、线上／线下方式、可选照片。
- 提供帮助者主动申请，求助者选择一位负责人；第一版每个求助仅有一位有效负责人。
- 可查看申请人的自愿公开技能与服务介绍；自填技能不显示成专业资格认证。
- 接受后可以发起关联私聊，沿用私聊接收同意机制；未建立聊天时可通过业务记录继续查看状态。
- 负责人提交处理说明后，由求助者确认解决；未解决可继续处理或申请协调。
- 认领后无法继续时，提供说明并申请退出，由求助者确认；长期无回应可由管理员记录依据后协调释放。

**状态：** 待审核 → 待认领 → 处理中 → 待求助者确认 → 已解决。另有已退回、已撤销、已过期；协调作为独立标记，保留处理记录。

**验收：** 重复点击或同时接受两人不会产生两个负责人；提供帮助者不能自行将求助标记为已解决；参与者只看得到有权访问的记录与附件；有延期、撤销和协调入口。

## 3. 规范岗位卡

**场景：** 老乡浏览招聘信息时，最关心工作地点、工资组成、上班时间和实际用工方。

- 入口：现有“求职招聘”分类增加岗位专用发布表单和筛选。
- 必填字段：用工单位、岗位名称、工作区县、薪资范围或面议、计薪单位、工作时间、用工类型、要求、截止日期。
- 发布人注明本人身份：企业直接招聘／受委托发布／信息转发；分别展示，不使用统一的“认证企业”标识。
- 可选字段：食宿、社保、技能要求、来源链接；具体地址可以在双方联系后告知。
- 求职者点击“表达意向”，提交简短自我介绍；初版不强制上传简历和证件。
- 发布者查看本人岗位收到的意向、反馈是否继续沟通，并及时标记招满或暂停。
- 到期岗位退出默认招聘结果；岗位的重要条件变更后重新审核，已表达意向者能够看到变更。

**状态：** 待审核 → 招聘中 → 暂停／已招满／已到期。求职意向单独记录为已提交、已查看、继续沟通、暂不合适、已撤回。

**验收：** 按工作地点和用工类型筛选准确；面议不按零工资展示；平台审核与用工资质核验明确区分；意向资料仅本人和岗位发布者等授权处理人员可见；过期岗位不能继续投递。

## 4. 活动出行卡

**场景：** 会员报名后，希望出发前在一个页面看到全部到场信息。

- 入口：报名成功页与“我的活动”中的“出行与集合”。
- 集中展示活动日期、集合时间、地址、入口照片、公交／停车说明、已确认的组织者联系渠道、签到入口。
- 支持“加入日历”：H5／电脑提供日历文件，小程序按可用能力提供复制日程或保存提醒卡；不承诺所有设备均能直接写入系统日历。
- 用户可自愿选择组织者设置的集合点，例如地铁出口；仅组织者查看参与者名单，成员端显示人数和组织者信息。
- 活动地点有可靠坐标且日期在预报范围内时展示当地天气；超出范围显示预报暂不可用，不能套用用户当前城市天气。
- 活动改期、改址或取消后，站内通知关联原报名记录；出行卡始终显示最新安排和变更时间。

**验收：** 不把集合点报名等同于活动签到；活动取消后签到入口关闭；历史日历文件明确提示以活动页最新安排为准；集合点名单不会公开暴露手机号。

## 5. 便民服务名片

**场景：** 会员需要找到愿意提供家电维修、摄影、翻译、设计等服务的老乡。

- 入口：会员名录增加“按服务找人”，会员可自愿创建服务名片。
- 字段：服务类别、服务地区、可联系时段、服务说明、公益／收费、收费说明、可选作品图片。
- 支持暂停接单、更新可用时间；平台显示最后更新日期。
- 普通列表按相关性和更新时间展示，商业推广沿用广告审核和明确标识。
- 联系采用现有私聊申请或联系方式交换；填过入会手机号不等于允许公开服务电话。
- 初版提供需求咨询，不接入平台代收费用；如涉及服务资质，应分别标明自述信息与已核验材料。

**验收：** 暂停服务可见明确状态；作品隐藏后不通过缓存名片继续展示；普通服务名片与广告可区分；关闭名录或服务公开后，查询结果及时更新。

## 6. 特产到货预告与自提预约

**场景：** 老乡想知道家乡产品何时有货，购买后需要安排方便的取货时间。

- 商品详情支持订阅到货提醒、查看预计到货日期和更新记录；预告不自动生成订单或扣减库存。
- 商品真正上架且有库存后才通知订阅者；修改预估日期时可合并通知，用户可取消订阅。
- 已确认的自提订单可选择取货地点和可用时段；管理员配置各时段的接待数量。
- 订单备妥后生成自提凭证，展示商品、数量、地点、时段；凭证仅供本人及授权履约人员访问。
- 管理员扫码前先核对订单，系统单独保存线下结算与交付状态；扫码不会自动变成“已付款”。
- 代领由买家主动生成可撤销的限时凭证，避免转发完整订单地址和联系方式。

**验收：** 库存不足不能下单；预约不会重复占用名额；订单取消时释放预约；凭证核销幂等、不能重复交货；核销人员只具备必要履约权限。

## 7. 共建项目执行公示

**场景：** 会员认领了物资或志愿服务，希望了解是否收到、如何使用、项目是否完成。

- 入口：众筹项目详情增加“执行进展”。
- 发起人创建里程碑，例如物资准备、配送、现场服务、结果整理，填写负责人和计划日期。
- 物资展示目标数量、有效认领、已核实交付；服务展示目标工时、认领工时、已核实完成工时。
- 资金只展示资金意向汇总，并明确“意向未收款”；物资、工时、资金分别计算，不能相加成一个完成率。
- 发起人上传进展照片与说明，由授权人员审核后公开；出现延误时更新原因和下一步安排。
- 结项提供成果摘要与实际完成记录；公开页面隐藏认领者联系方式和受助人的私人信息。

**验收：** 取消认领后同步更新数量；未核实记录不计入实际交付；公开图片必须通过审核；更正公示保留时间与原因；进展通知只发送给有权查看的订阅者。

## 8. 失物招领与认领核验

**场景：** 活动现场或日常生活中遗失、拾获物品，需要寻找失主并安全交接。

- 入口：互助页增加“寻物／招领”类型，并可关联活动。
- 公开字段：物品大类、模糊地点、时间范围、描述、可选照片；证件号码、钥匙细节和完整联系方式不公开。
- 拾获者保留一项可验证的细节，认领人私下填写特征说明；其他申请人不能查看彼此答案。
- 双方确认后通过已有联系方式交换或私聊安排交接；不得直接公开陌生人的联系资料。
- 发布者可标记已找回、已交接或已移交场地方；管理员处理冒领举报。

**状态：** 待审核 → 寻找中 → 已找回／已交接／已移交／已关闭。认领申请单独审核，不自动改变物品状态。

**验收：** 认领答案不进入公开搜索或通知摘要；图片预览提示遮挡证件信息；关闭信息后停止接受新认领；位置授权拒绝时仍能手动填地点。

## 手机端统一设计

- 首页以“找活动、找帮助、找工作、办事情”作为服务快捷入口，低频功能归入现有模块；不为每项提案新增底部导航。
- 发布入口先选择任务，再显示对应短表单；同一份招聘信息或求助只保存一条业务记录，多入口展示时指向同一详情。
- “我的”集中展示进行中的事项及下一步操作；“已读通知”和“已经办完”分别记录。
- 提供标准／大字两档显示，支持系统字号；正文、按钮和表单一起适配，图片中的文字不作为唯一说明。
- 正文、长标题、输入法弹出、320px 小屏和横屏均检查布局；主要触控区域至少 44 CSS px，不能只增大字号而压缩点击区域。
- 草稿按账号隔离，可由用户清除；退出登录后不能向下一位登录者显示上一位的表单或附件。
- 定位、相机和通知权限分别在使用时申请；手动选城、选图、站内查看作为可用路径。

## 实施顺序与共用能力

1. **补齐基础衔接**：盘点“我的”现有记录，统一详情跳转；实现站内业务通知、订阅关闭与状态失效提示。岗位、求助等功能只能在该基础上承诺对应提醒。
2. **第一组试点**：新人服务包、老乡帮办、规范岗位卡。先围绕少量真实指南、明确的求助类别和愿意维护岗位的发布者运行。
3. **第二组体验**：活动出行卡、大字模式、便民服务名片。先验证手机使用，再扩展分类和集合点管理。
4. **第三组运营**：到货与自提、共建执行公示、失物招领；具备稳定履约和审核负责人后开放。

业务通知需有事件标识以防重复发送；点击时重新校验目标权限与状态。首版在站内展示，微信订阅消息待真实 AppID、平台模板和用户授权具备后接入，不能把站内通知写成手机离线推送。

所有方案继续使用现有超级管理员、普通管理员、组织者及板块版主的权限边界。版主只处理授权板块；新增帮办协调、订单核销等权限需要显式配置，不能由“能登录管理端”推导出全部操作权限。

## 怎样验证是否实用

建议先邀请新会员、常用会员、组织者各 3～5 人完成真实任务，记录完成时间、卡住的地方与是否需要他人帮助。这是建议的验证方式，目前未开展。

| 试点 | 主要观察指标 | 必须同时观察 |
| --- | --- | --- |
| 新人服务包 | 已保存清单中，用户确认完成至少一项的比例 | 过期指南数量、失效链接、需要人工解释的步骤 |
| 老乡帮办 | 有效求助的首次响应时长、由求助者确认解决的比例 | 长期未回复、撤销、协调与重复求助 |
| 规范岗位卡 | 有效意向获得发布者回应的比例 | 过期岗位、岗位条件不一致反馈、用户撤回原因 |
| 活动出行卡 | 报名后到场率、现场重复问路的数量 | 改期通知是否被看到、签到失败原因 |
| 自提预约 | 预约时段内实际完成交付的比例 | 改约、爽约和凭证核销失败 |
| 执行公示 | 到期里程碑按时更新比例 | 认领与实际交付的差异、未核实记录 |

试点前先记录现状，再比较改善；样本过少时展示人数及具体反馈，不据此宣称大幅增长。实际开发须对状态流转、并发操作和数据权限做回归，并完成安卓微信、iPhone Safari 与微信小程序真机验收。
