# 沭阳之家实用功能增量设计

日期：2026-11-02。设计基线：v1.5.1。状态：F01、F02、F04、F07基础版随v1.6.0交付；其余条目为后续规划。各项实际交付与限制以《事项中心与互助办结-v1.6.0》为准。

用户已确认同时覆盖三类需要：会员日常使用、管理效率、社区互助。具体场景根据现有需求文档和业务代码推导，尚未进行真实会员访谈或采集使用数据；下列优先级为建议，效果指标为后续验证口径。

## 设计依据

系统已有入会审核、会员名录、活动报名和签到、互助发布、资源交换、论坛、聊天和表情、众筹、联系方式交换、订单、文件导入导出及打印。新功能围绕这些业务补足使用流程。

| 当前情况 | 使用上的缺口 | 本次设计方向 |
| --- | --- | --- |
| 个人中心已有报名、志愿时长、互助统计；订单、交换、认领等记录在各模块 | 会员要逐页查找自己还有什么事情没办 | 统一“我的事项”和下一步操作 |
| 聊天已有未读数；公告是公共内容 | 审核结果、提货、对方确认等业务变化缺少统一收件入口 | 站内业务通知及独立已读状态 |
| 工作台已有分类导航；顶部待处理数只统计待审会员和互助帖子 | 活动申请、论坛、资源、广告等事项容易遗漏 | 按角色汇总全部可处理任务 |
| 互助已有求职招聘、资源合作、生活互助、家乡分享分类，及关闭操作 | 结构化筛选、实际解决结果、过期维护不足 | 在原模块增加模板和办结状态 |
| 已有活动容量、报名取消、订单履约和报表 | 候补补位、到场准备、反复筛选仍依赖人工 | 补充组织工具，复用现有报名与报表 |

不另建重复的招聘站、订单系统或聊天系统；本轮方案优先让已有业务更好用。

## F01 我的事项：知道接下来做什么

**场景**：会员报名了一场活动、买了特产，又向老乡申请了交换，希望打开“我的”就知道下一步。

入口为“我的”首屏；保留电子会员卡，增加“需要我处理／等待对方／近期安排／已结束”。条目显示业务类型、标题、明确状态、更新时间和一个主要操作。时间固定按北京时间显示。

首版聚合活动报名、本人互助、订单、资源交换、联系方式交换和众筹认领。按“有截止时间的待办 → 其他待办 → 即将开始的安排”排序；已结束记录进入历史页。待审入会者只看到本人入会进度与可修改资料入口。

| 示例状态 | 展示文案 | 主要操作 |
| --- | --- | --- |
| 订单已备妥自提 | 可以取货了 | 查看取货信息 |
| 对方提出联系方式交换 | 有老乡希望认识你 | 查看来意 |
| 互助被退回 | 请补充信息：具体原因 | 修改并重新提交 |
| 本人尚未确认交换交付 | 请核对实际交接情况 | 查看交换记录 |
| 报名活动即将开始 | 明日14:00，集合点…… | 查看集合信息 |

聚合页读取各业务当前状态，不另外维护一套可编辑的“完成状态”。已读通知不会完成待办；点击条目后重新校验权限与原业务状态。某模块加载失败，只对该模块提供重试，不能把失败显示成“没有待办”。

**验收**：在“我的”一次进入可见全部待办类型；切换账号不残留前一人的数据；已在另一端处理的事项刷新后更新；源记录失效时明确提示；数量与各业务状态一致。

## F02 业务通知：看见变化，直达原记录

入口沿用“消息”，增加“聊天／业务通知”两个页签；桌面顶部铃铛进入业务通知，公共公告保留原入口。两个页签分别统计未读数，聊天的会话与权限不变。

首版通知事件：入会和内容审核结果、活动报名结果／取消／集合地点变更、订单发货／可自提／取消、资源及联系方式交换处理结果。普通回帖和关注更新放到后续，避免首版产生大量低价值提醒。

每条通知包含“发生了什么、何时发生、去哪里查看”；如“你报名的活动已取消，点击查看说明”。列表支持未读筛选、单条已读、当前查询结果截止此刻的全部已读；新到达消息不被一起清除。打开原详情成功后再标记该条已读。

业务状态变化和待发送通知在同一事务中记录，再重试分发；按“收件人＋业务编号＋变化版本”去重。通知目标使用站内业务类型及编号，访问时重新鉴权，内容撤下后不继续展示受限正文。业务失败不得生成成功通知。

首版为站内持久通知，前台刷新，后台停轮询；下次进入仍能看到。微信订阅消息需实际AppID、授权和通道配置，作为独立扩展；站内通知不能宣称手机离线推送。

**验收**：重复提交／分发重试只产生一条通知；两端已读状态同步；活动取消只通知受影响报名者；撤销授权后不能借通知查看私密数据；“已读”与“已完成”明确区分。

## F03 收藏与发布草稿：方便下次接着用

收藏首批支持活动、互助、资源、论坛主题、商品；入口为详情页“收藏”和“我的收藏”。按类型筛选、搜索和取消，跨设备同步。收藏不等于报名、占用库存或关注所有更新；来源被撤下时显示“内容暂不可用”，不保留已无权阅读的正文。

草稿首批覆盖互助信息与活动申请，采用登录后的服务端私有草稿；输入停止后自动保存，并显示“保存中／已保存时间／保存失败”。离开时如有未保存内容，提供“重试保存／继续编辑／放弃”。上传附件后才记录已完成上传的引用，不保存文件选择器句柄。

成功提交审核后删除对应草稿；多端编辑使用版本号检测冲突，让用户选择保留当前内容或查看服务器版本，不静默覆盖。草稿始终只对作者开放，退出时清空内存；不把密码、收货地址或私人聊天顺带纳入草稿功能。

**验收**：重复收藏不重复计数；隐藏内容不从收藏泄漏；刷新后草稿恢复；网络断开时不显示“已保存”；两端冲突可恢复；提交失败仍保留草稿。

## F04 管理待办总览：减少漏处理

工作台默认进入“待办总览”，保留现有会员服务、内容与活动、运营协作、数据管理四组导航。首版合并会员入会、互助、活动申请、论坛主题及回帖、资源、广告、众筹审核，并为有订单权限者展示待确认／待履约订单。

每条包含对象摘要、来源模块、提交时间、等待时长、当前状态、处理入口。提供“全部／等待较久／按类型”筛选；默认按提交时间从早到晚。组织者仅见原权限允许的内容，版主仅见自己板块，订单信息不因进入总览向所有组织者开放。

首版不增加强制领单，避免小团队多一道步骤；确有多人重复处理后，再补“我负责／未分配”和转交记录。超时标记用于提示，不能自动批准或拒绝。现有顶部“待处理”数改用同一权限与状态口径。

**验收**：每类待办都能跳转到准确记录；总数与筛选列表一致；另一管理员先处理后，第二人提交收到已处理提示；禁用或收回角色后立即失去相应查看和操作权限。

## F05 批量处理与常用意见：少重复，也能逐项核对

首批用于会员入会和互助审核。支持勾选当前可处理项，预览标题／申请人及拟执行动作，再确认提交；“全选本页”和“全选筛选结果”分开，首版只提供本页，建议每批最多20条。

常用退回意见如“请补充具体地点”“请说明服务时间”，选择后可修改；会员审核不默认勾选通过，意见不能代替核验。角色授权、账号停用、密码重置、资金或结算操作保留单独确认流程。

批量结果逐项显示成功、状态已变化、无权限或失败原因；重试只处理失败项，复用请求编号。每条保留操作者和理由。此处允许逐项成功，与现有Excel导入的整批校验规则区分，确认页要说明。

**验收**：选中后对象状态变化不会被覆盖；筛选变化清除过期选择；一次操作产生逐条审计；重试不重复执行已成功项；窄屏展示可读的结果卡片。

## F06 活动组织助手：从报名到到场

**第一步：行前准备**。报名成功页提供集合点、联系人、需携带物品和“加入日历”。Web／H5可下载ICS；小程序按实际支持提供文件或复制时间地点。ICS包含明确时区和稳定活动编号；导入的是一次快照，活动取消或修改后由站内通知提示更新，不宣称系统日历自动同步。

组织者活动页增加“已报名／已签到／未签到”筛选、实际到场进度，并复用已有名单导出打印。集合点修改需要说明并通知已报名者；现有“已有报名不可改时间和类型”约束继续保留。

**第二步：候补补位**。满员后可自愿加入候补；按加入顺序发出补位邀请，明确展示“候补中”或“请在某时前确认”，确认成功才算报名。一个会员同场只能有一条有效报名或候补。

状态流转：候补中 → 获得补位邀请 → 已报名；也可主动退出、邀请超时、活动取消。邀请期间预留名额，计算容量时计入有效预留；直接报名不得抢走已预留名额。建议默认确认期限12小时，实际截止不晚于活动报名关闭或开始时间；不足1小时不再自动邀请，由组织者联系后在本人明确确认基础上操作。

补位调度需持久化到期时间并定时补扫，服务重启后可恢复；名单与预留在事务中更新。活动取消清理预留并通知候补者；邀请不等于签到，组织者不能替会员伪造同意。首版仅站内提醒，试点时组织者仍需关注未打开邀请者。

**验收**：多人同时退出、确认和直接报名不超员；重复确认只占一名额；超时释放且按顺序邀请下一位；取消活动停止补位；境外时区和手机端展示同一实际截止时间。

## F07 互助信息办结：让信息保持有效

沿用互助广场，增加按分类选择的填写模板：求职招聘填写岗位／期望岗位、地区、薪资范围、工作时间；生活互助填写所需帮助、片区、希望完成时间；资源合作填写可提供、所需条件和可协商时间。薪资可选“面议”，必填项随求职／招聘身份变化。

增加“还需要帮助／处理中／已解决／已过期”业务状态，与“待审核／通过／退回／下架”审核状态独立。首版由发布者更新业务进度，不能自行恢复被下架内容；旧“关闭”记录保持已关闭，不能批量当作已解决。

建议有效期默认30天，可选7／30／90天；到期不再进入有效信息列表，仍可在本人历史中查看和申请续期。实质修改重新审核；原文保留版本便于追溯。帮助者通过现有聊天／联系方式申请联系，遵守原有同意流程。

“已解决”由发布者确认，可写一句结果或自愿致谢；标记错误可说明原因重新打开并重新检查有效期。互助筛选支持分类、片区、有效状态；不要求精确住址。基础版先做状态、有效期、筛选和修改重审，详细招聘模板随后完善。

**验收**：标记已解决后不再出现在默认“还需要帮助”；自动过期不统计为解决；退回后可编辑重提，公开版本不被未审核修改替换；被下架条目不能通过续期绕过审核；旧记录兼容。

## F08 会员技能与可帮助时段：找到愿意帮的人

在会员资料新增可选“我能提供的帮助”，建议最多5个技能标签，例如摄影、简历修改、水电维修、电脑使用、活动组织。另选服务片区、线上／线下、可帮助时段及“暂不接收请求”。这是会员自述，不等于平台资质认证。

在老乡名录增加技能、片区、当前是否愿意帮助的筛选；仅纳入已审核、已启用、主动公开资料并开启帮助展示的会员。默认按相关标签匹配和明确的稳定排序展示，不制作“最佳老乡”排名。

申请方填写具体问题和期望时间，对方选择愿意沟通或暂不方便，再沿用已有私聊／联系方式交换。增加频次限制和取消、拒绝入口；关闭帮助展示立即停止新申请，不向申请方公开注册手机号。

**验收**：关闭公开后搜索不可见；暂停时不接受新请求；同一双方不重复堆积待处理请求；被屏蔽关系不可绕过；通知和申请不包含未经授权联系方式。

## F09 生活指南与材料清单：减少来回跑

入口放在“互助 → 生活指南”，先覆盖居住证、社保查询、租房、就医、子女入学和劳动咨询，按苏州区县选择适用范围。每篇须包含适用对象、步骤、材料、办理入口／地点、官方来源、核对日期和维护人。

会员可收藏指南、勾选材料清单，仅保存“已准备／未准备”状态，不要求上传证件。官方政策以原文为准；页面提供“信息有变化”反馈。小程序无法打开外链时提供可复制链接和来源名称，不能以空按钮代替可用操作。

没有核实过的内容不预置成正式指南；先由运营选3～5篇高频事项试点。每篇设置复核日期，逾期显示“待复核”，停止在首页推荐但保留来源入口。

**验收**：区县切换不会混用另一地区的条件；来源和核对日期始终可见；个人清单互不影响；政策改版时提示重新核对材料；运营能查到逾期文章及负责人。

## F10 反馈与处理进度：提交问题后有着落

“我的 → 帮助与反馈”用于系统问题、业务咨询、内容举报和相册撤图；内容详情也提供关联举报入口。首版支持说明和可选图片，自动关联业务编号，不自动附带聊天全文或无关会员资料。

用户提交后获得编号，流程为“已提交 → 处理中 → 待补充／已回复待确认 → 已关闭”。运营受理后可回复、请求补充或转交有权限人员；申请人可补充、确认解决、撤回及在关闭后7天内申请重开。关闭须有结果说明，不因已读自动关闭。

举报处理和账号／内容处置是两个动作：处理者只能调用原有授权范围内的处置入口，不能因为接到工单就获得全站管理权限。普通反馈作者可查看自己的记录；内容举报仅负责人员可见，通知被举报方不泄漏举报者身份。与处理人本人有关的举报交由另一名有权限人员处理。

**验收**：编号可追踪；补充和回复按时间显示；越权查看被拒绝；重复点击提交不重复建单；撤图完成后原图片入口失效；没有服务承诺前不显示虚构的预计解决时间。

| 页面 | 建议结构 |
| --- | --- |
| 首页 | 保留乡情内容与活动推荐；登录后增加一条“你有N件事待处理”，避免堆叠全部新入口 |
| 我的 | 会员卡 → 我的事项 → 我的收藏／草稿 → 参与历史 → 资料与帮助 |
| 消息 | 聊天／业务通知两个页签，各自未读数 |
| 互助 | 有效信息／找人帮忙／生活指南；清楚区分需要帮助和提供帮助 |
| 管理工作台 | 待办总览为默认页，原四组业务导航保留，反馈与指南管理按角色显示 |

Web继续使用Element Plus表单、页签、状态标签与表格，保留沭阳之家标识和深蓝暖金特色。手机底部维持“首页／活动／互助／我的／消息”五项；窄屏任务用卡片，筛选用可关闭面板，主操作至少44px高。H5和小程序沿用各自兼容控件，共享业务规则与状态文案。

所有页面提供首次空状态、筛选无结果、加载失败重试和失去权限状态。弱网操作显示进行中，失败保留输入；登录过期后重新登录可回到目标，但不得恢复另一账号的私有草稿或数据。

## 实施顺序与交付边界

| 阶段 | 建议范围 | 完成条件 |
| --- | --- | --- |
| 第一批 | F01我的事项、F02核心业务通知、F04管理总览、F07互助办结基础版 | 三类人群都有完整入口；申请／处理／通知／进度形成闭环；权限与旧数据回归通过 |
| 第二批 | F03收藏和草稿、F05批量审核、F06行前准备、F08技能帮助、F10反馈 | 中断可恢复、处理有结果、互助可找人；逐功能交付，避免一次堆叠 |
| 第三批 | F06候补补位、F09经核实的生活指南、按反馈完善招聘模板 | 候补并发及调度恢复测试通过；指南有明确维护人员和内容复核周期 |

开发依赖：先统一可跳转的业务目标和服务端权限判断，再做只读聚合；通知持久化与去重支撑业务提醒；候补依赖通知和可恢复的到期调度。聚合列表需按权限分页，不能让手机先下载全站会员或私有业务数据再过滤。

现有各业务记录仍为状态来源；收藏、草稿、通知和工单独立保存。新增记录要兼容旧数据缺失字段，重试需幂等，账号切换继续沿用已有请求作用域保护；更新方案不得把本地未提交改动一并带入发布。

下一次实际发布兼容功能时，从当时最新版本递增minor；若仍以1.5.1为基线则候选为1.6.0。这里只做产品设计，不提前占用版本标签，不把设计文档当成功能完工记录。

## 验收与价值验证

| 维度 | 必测或观察项 |
| --- | --- |
| 会员完成任务 | 从“我的”最多两次点击进入目标业务详情；状态和下一步动作可理解 |
| 管理效率 | 按类型记录提交至首次处理、提交至办结的中位数及较慢任务耗时；与上线前基线比较 |
| 互助成效 | 发布者明确确认已解决的有效信息数／同期审核通过信息数；关闭、过期不得冒充解决 |
| 活动使用 | 候补邀请确认率、确认后到场率、过期释放是否正确；与普通报名区分 |
| 可用性 | 320／390／768／1440px、横屏、短视口、弱网、离线后恢复、海外时区、两内核；小程序另做真机验证 |
| 一致性 | 并发处理、重复点击、过期响应、跨设备更新、重启后调度恢复、账号和角色变更 |

首批上线前邀请会员、组织者和管理员各试用典型任务：查提货信息、找待处理申请、关闭已解决求助；记录是否需要解释、误点位置与完成耗时。效果以实际记录为准，不预填节省时间、活跃提升或满意度数字。
